# 개인 연구용 TVC 프로젝트 확장 로드맵

작성: 2026-09-07. 원본 검토 기준: `5cff917900f27b2e5b21c164b132abaccfa6da86`.
아래는 원본 설명을 그대로 옮긴 제작 지침이 아니라, 코드 검토와 공식 자료를 바탕으로 한 연구 제안이다.
성능 향상·논문 신규성·특정 센서의 최종 적합성은 아직 검증되지 않았다.

## 추천 결론

**주제 A: 액추에이터 지연·포화·모델 오차에 강인한 동축 TVC 제어.**
우선 원본 LQI를 기준선으로 두고 구동기 모델을 식별한 뒤, 지연 상태 확장 LQI와 제약 MPC를 비교한다.
그 다음 **주제 B: 비전/IMU/거리센서 융합을 이용한 GPS 없는 위치 유지·정밀 착륙**을 결합한다.
두 주제를 동시에 처음부터 구현하지 않는다. 제어기 비교 중에는 위치 추정기를 고정하고,
추정기 비교 중에는 제어기를 고정해야 개선 원인을 구분할 수 있다.

고가 센서를 살 수 있다면 반갑지만, 우선 투자처는 추력·서보 특성 측정과 독립적인 기준 위치 측정이다.
기체가 실제로 어떻게 움직였는지 측정할 수 있어야 제어기의 개선을 입증할 수 있다.

## 원본에서 먼저 바로잡아야 할 기준선

| 코드에서 확인한 사실 | 연구에서 처리할 방법 |
|---|---|
| `lqr_compute.py`는 8개 물리 상태와 4개 적분 상태의 12상태 LQI | 이름보다 실제 상태·입력·적분·클리핑 방식을 기준으로 비교한다. |
| `sim.py`의 질량은 0.399 kg, LQI 계산은 0.430 kg이며 관성·레버암도 다름 | 파라미터 파일을 하나로 통합하고 출처를 실측/CAD/가정으로 표시한다. |
| `sim.py`에는 `m*g*L/I`의 기울기-각가속도 항이 있고 LQI 계산에는 없음 | 고정 지점에 매단 시험과 자유비행 모델을 구분해 Newton–Euler 식부터 다시 유도한다. |
| 계산된 K와 펌웨어 K의 최대 절대 차이가 약 0.005775 | 게인 생성 조건/파일 해시를 기록하고 펌웨어와 자동 비교한다. 차이 자체가 비행 불안정을 증명하는 것은 아니다. |
| yaw 입력은 계산 코드에서 kg 계열 설명, 그래프에서는 Nm로 표기 | SI 단위와 모터 차동추력→요 토크 변환을 끝까지 추적한다. |
| 센서 보정/트림/서보 오프셋과 게인이 코드에 직접 들어 있음 | 본인 기체의 보정값·파라미터로 분리한다. 원본값을 그대로 이식하지 않는다. |
| 펌웨어 빌드에 착륙 속도·고도 기준 중복 정의 경고가 있음 | 상태 전이/착륙 기준을 하나의 설정으로 정리하고 시험한다. |

자유비행에서 중력은 질량중심에 작용한다. 따라서 "추력 장치가 무게중심 아래에 있으므로 중력이
자동으로 전복 토크를 만든다"는 고정축 역진자 설명을 그대로 쓰면 안 된다. 추력 작용점·방향에 따른
`r × F`, 로터 반작용 토크, 관성 결합을 모델링해야 한다. 자유비행에도 자세 제어는 필요하며,
이 지적은 기체가 저절로 안정된다는 뜻이 아니다. 이 판단은 코드 차이와
[MIT의 질량중심 기준 비행체 동역학](https://vnav.mit.edu/material/06-Control1-notes.pdf)에 근거한다.

원본의 두 모터와 2축 TVC는 입력이 네 개다. 일반적으로 순간적인 힘·토크 6개를 모두 독립적으로
지정할 수 있는 완전 구동 구조가 아니다. MPC나 PX4를 붙여도 입력 수가 늘지는 않는다.
위치와 자세를 완전히 독립 제어하는 것이 목표라면 기구 구조부터 다른 연구가 된다.

## 연구 후보와 실험 설계

| 우선순위 | 연구 질문 | 구현 방향 / 재사용 | 비교·평가 |
|---|---|---|---|
| 1 | 실제 서보 지연·백래시와 추력 변화가 제어 성능을 얼마나 제한하는가? | 원본 LQI + 측정 기반 구동기 모델. 서보 각도/각속도 제한, 전압별 추력곡선, 동축 간섭을 포함 | 동일 초기 자세·외란에서 RMS, 최대 이탈, 정착시간, 포화 비율, 전류 사용량 |
| 2 | 제약을 미리 고려하면 늦은 구동기에서도 안정 범위를 넓힐 수 있는가? | 지연 상태 확장 LQI → 선형 제약 MPC → 필요할 때 비선형 MPC. [acados](https://docs.acados.org/) 활용 후보 | 같은 응답 속도/입력 비용에서 제약 위반, 모델 오차 허용범위, 계산시간 p99/최대값 |
| 3 | 바람·질량/무게중심 변화에 덜 민감하게 만들 수 있는가? | 외란 관측기 또는 INDI. [Paparazzi INDI 구현](https://wiki.paparazziuav.org/wiki/Working_with_INDI) 참고 | 동일 제어 주기와 필터 지연에서 외란 회복, 노이즈 증폭, 입력 떨림 |
| 4 | 비전 위치 정보가 늦거나 끊겨도 위치 유지·착륙을 지속할 수 있는가? | [OpenVINS](https://github.com/rpng/open_vins) + 거리 보조 + [AprilTag](https://github.com/AprilRobotics/apriltag) 착륙 목표 | 독립 기준계 대비 위치 오차, 드리프트, 착륙 오차/속도, 추적 손실률, 종료 안전성 |

INDI에는 이미 MAV 외란 억제 실험을 다룬
[Smeur 등의 논문](https://arxiv.org/abs/1701.07254)이 있다. 따라서 "INDI 적용" 자체를 신규성으로 삼기보다,
느린 TVC 서보와 빠른 모터가 공존하는 구조에서의 지연·필터 정합과 제어 효과 추정에 초점을 맞춘다.
각가속도 피드백에는 노이즈와 필터 위상 지연 문제가 있으므로, 모델을 전혀 몰라도 되는 방법으로 취급하지 않는다.

제어 할당 역시 선행 연구가 있다. 예를 들어
[2026년 동적 제어 할당 프리프린트](https://arxiv.org/abs/2604.05677)는 포화와 구동기 동역학을 다룬다.
다만 그 연구는 각 프로펠러가 두 축으로 기울어지는 중복 구동 헥사로터의 수치 실험이며,
이 저장소의 동축 TVC에 그대로 적용되는 결과가 아니다. 본 프로젝트에서는 입력 부족, 동축 공력,
실제 서보 지연을 고려한 모델과 실기 검증을 차별화 후보로 삼는다. 체계적인 선행 연구 검토 전에는
논문으로 충분히 새롭다고 단정하지 않는다.

## 센서와 기구에 돈을 쓴다면

| 투자 항목 | 기대하는 역할 | 구매 전에 확인할 점 |
|---|---|---|
| 지그·로드셀·전류/전압 측정 | 추력곡선, 전압 저하, 동축 로터 간섭을 실제로 측정 | 총 추력은 모터 단품 수치의 단순 합으로 확정하지 않는다. 보호 지그와 원격 차단 필요 |
| 저백래시 구동부 + 각도 피드백 | 명령한 TVC 각도와 실제 각도의 차이를 측정하고 보상 | 무부하 속도가 아닌 프로펠러 구동 부하에서의 지연/토크, 기어비, 전원 순간 전류 |
| 글로벌 셔터 카메라 + IMU | GPS 없이 이동량을 추정하는 VIO | 하드웨어 타임스탬프·동기화, 노출, 렌즈/IMU 외부 보정, SDK/드라이버, 질량·전력 |
| 하향 거리센서 | 착륙 직전 지면까지의 거리 보조 | 최단 거리, 지면 반사율/햇빛, 자세에 따른 기울어진 거리, 측정 주기 |
| 외부 카메라/모션캡처 | 제어/추정 성능을 평가하는 독립 기준계 | 가림, 시야, 공간 보정, 시간 동기화. 기존 연구실 장비 사용이 가능하면 우선 활용 |
| 산업용 IMU | 온도·바이어스·노이즈가 실제 병목일 때 개선 | 진동 절연/필터/타임스탬프 문제가 먼저인지 확인. IMU만으로 절대 위치를 장시간 유지할 수는 없음 |

구체적인 카메라 후보로는 [RealSense D455](https://www.realsenseai.com/products/real-sense-depth-camera-d455f/)를
책상 위 VIO 평가용으로 검토할 만하다. 공식 설명은 글로벌 셔터와 내장 IMU를 제시하지만,
최대 해상도의 최소 깊이 거리가 약 52 cm이므로 착지 직전 거리센서 하나를 대체한다고 가정하면 안 된다.
또한 SDK에서 깊이를 출력하는 것과 기체 위치를 안정적으로 추정하는 VIO는 별도 기능이다.
제품 페이지의 URL/제품 표기가 혼재하므로 구매 시 D455/D455f의 정확한 SKU와 데이터시트를 다시 확인한다.

고급 IMU 비교 후보는 [ADIS16470](https://www.analog.com/en/products/adis16470.html) 같은 계열이다.
지금 바로 선정하기보다는 현재 IMU의 정지/구동 중 로그를 보고 필요성을 결정한다.
고가 기준계는 Vicon/OptiTrack 계열도 후보이며,
[PX4의 외부 위치 입력 문서](https://docs.px4.io/main/en/ros/external_position_estimation)처럼 좌표계와 지연 정합을 해야 한다.
측위 입력에 쓰는 같은 센서의 값을 그대로 정답으로 놓고 평가해서는 안 된다.
카메라 한 대 + AprilTag는 제한된 실험의 기준계로 쓸 수 있지만, 보정 오차를 포함하므로 모션캡처와 동급으로 간주하지 않는다.

카메라·IMU 시간 오차가 성능에 큰 영향을 준다는 점은
[OpenVINS 보정 가이드](https://docs.openvins.com/gs-calibration.html)에서도 강조한다.
카메라의 가격/해상도만 높이는 것보다 시간 동기화와 캘리브레이션을 먼저 확보한다.

기체에 컴퓨터·카메라·DC/DC·배선·지지대까지 추가하면 질량, 무게중심, 관성, 전류 소모가 달라진다.
원본 약 0.4 kg 모델에 단순히 더 싣는 것으로 계획하지 않는다. 완성 질량과 배터리 전압 하한에서의
실측 총 추력을 확인하고, 기울어진 상태의 수직 추력 여유까지 계산한 후 필요하면 추진계/프레임을 재설계한다.
기체에 올릴 컴퓨터도 이 예산을 정한 뒤 고른다. 첫 VIO/최적화 실험은 노트북에서 할 수 있다.

## 개발환경과 오픈소스 재사용 전략

연구용 OS는 **Ubuntu 24.04 LTS + ROS 2 Jazzy + Gazebo Harmonic**을 우선안으로 둔다.
[PX4 공식 ROS 2 가이드](https://docs.px4.io/main/en/ros2/user_guide)는 24.04/Jazzy를 권장하고,
[Gazebo 호환표](https://gazebosim.org/docs/jetty/ros_installation/)는 Jazzy/Harmonic 조합을 제시한다.
카메라/보조 컴퓨터 SDK가 Ubuntu 22.04에 묶여 있다면 해당 장치의 환경을 먼저 확인하고 Humble 조합을 검토한다.
OpenVINS에 ROS 2 지원이 있다는 것과 모든 최신 배포판에서 즉시 빌드된다는 것은 다르다.
선택한 커밋의 빌드·공개 데이터셋 재생을 먼저 확인하고, 필요하면 추정기만 별도 환경으로 격리한다.

현재 PC의 WSL 설치/등록 오류를 해결해야 WSL2 경로를 사용할 수 있다. BIOS 가상화 상태도 재확인이 필요하다.
WSL2는 초기 소프트웨어 시뮬레이션 대안이고, 실물 USB 카메라·ST-Link 실험에는 네이티브 Ubuntu가 우선이다.
네이티브 설치는 별도 SSD/PC 또는 명시적으로 선택한 듀얼부트 방식으로 진행한다.
기존 Windows 파티션/BIOS는 이번 작업에서 변경하지 않았다.

권장 역할 분담:

```text
카메라/영상 IMU → Ubuntu 보조 컴퓨터: VIO·경로·실험 기록
                           ↓ 시간/좌표/품질 정보를 포함한 참조값·위치 추정
기체 IMU → 실시간 비행 제어기: 상태 추정·자세 안정화·구동기 제약·실패 대응
                           ↓
                      모터 2개 + TVC 2축

독립 외부 기준계 → 평가 로그 (제어 입력과 구분)
```

첫 단계에서는 원본 STM32 펌웨어와 LQI를 벤치 기준선으로 보존한다.
장기적으로는 PX4의 상태 추정·로그·안전 상태 관리·ROS 연동을 활용하는 경로를 검토한다.
하지만 원본 STM32 PCB는 PX4 지원 보드라고 확인된 것이 아니며,
원본 통신 프로토콜도 MAVLink/ROS가 아니다. 맞춤 TVC airframe과
[제어 할당 모듈](https://docs.px4.io/main/en/concept/control_allocation)의 구현/검증이 필요하다.
PX4 기본 쿼드로터 SITL의 성공은 TVC 기체의 성공이 아니다.

비전/경로 계산은 Ubuntu, 빠른 안정화와 통신 단절 대응은 기체 제어기에서 수행한다.
무선 GCS 통신 지연을 자세 제어 루프 안에 넣지 않는다. MPC를 보조 컴퓨터에서 실행한다면
기체 측 검증된 대체 제어기, 명령 유효기간, 계산 실패 처리를 먼저 설계한다.
제어 주파수는 무조건 높이지 말고 실측 센서/서보 대역폭과 최악 실행시간을 기준으로 정한다.

소프트웨어 구성별 역할은 다음과 같다.

- 원본: CAD/PCB/센서 드라이버/기구 구성 및 LQI 비교 기준.
- NumPy/SciPy: 모델 식별·선형 제어·재현 시험. 현재 설치와 실행 확인 완료.
- Gazebo/ROS 2: 맞춤 물리 모델, 센서 지연·노이즈 실험, rosbag 기록. 아직 설치/실행하지 않음.
- acados: 제약 MPC 후보. 아직 통합하지 않음.

## 다음 실행 순서와 통과 조건

실물 작업의 당장 실행할 순서와 입력 양식은 [실물 착수 체크리스트](실물-착수-체크리스트.md)를 따른다.

1. **모델 정합**: 좌표계(NED/ENU, body), SI 입력 단위, 질량/관성/추력·요 계수, 자유비행/고정 지그를 명시.
   합격 기준은 파라미터 한 곳에서 Python/C 설정 생성, 게인·입력 변환의 자동 비교가 통과하는 것.
2. **계측 가능한 벤치**: 프로펠러 제거 상태에서 센서·서보 방향·명령/실제 각도·시간 로그 확인.
   회전 추력 시험은 보호 지그/차폐/원격 차단을 준비한 뒤 별도 수행.
3. **물리 모델 검증**: 식별에 쓰지 않은 데이터로 추력·서보 모델 오차 검증. 원본 LQI 기준 응답 기록.
4. **제어기 비교**: LQI, 지연 확장 LQI, 제약 MPC 순서. 질량/관성/지연/전압 불확실성 스윕과 실패 사례도 기록.
5. **실시간 시험**: 계산시간 p99/최대값, 명령 만료, 센서 누락, 포화, 안전한 모드 전환을 SIL/HIL에서 확인.
6. **비전 분리 검증**: 공개 데이터셋 → 손으로 이동시키는 카메라 리그 → 독립 기준계 비교. 기체 탑재는 이후.
7. **제한 비행 → 정밀 착륙**: 안전 구역/차폐 또는 적합한 구속 시험에서 검증 후 점진적으로 확대.
   줄이나 지그가 주는 힘도 모델을 바꾸므로 구속 상태와 자유비행의 성능을 혼동하지 않는다.

모든 실험에 코드 커밋, 파라미터, 실제 질량/배터리, 센서 타임스탬프, 제어 주기 지터,
명령/추정/실제 구동 각도, 입력 포화, 위치 기준계, 실패 사유를 남긴다.
정량 목표 수치는 실측 기준선을 확보한 뒤 고정한다. 비행 전 KILL·명령 타임아웃·센서 오류 대응은 필수 점검이다.
